# Step 03 — theme and distribution contract

**Status: owner-approved planning baseline, not implemented or runtime-verified.** The owner accepted the proposed direction with two explicit requirements: default to the **system preference**, not forced light, and give Dialogs opened from nested theme scopes the **originating theme treatment** even when teleported. Follows the [Step 01 audit](audits/01-public-surface.md) and [approved Step 02 token baseline](STEP_02_TOKEN_CONTRACT.md); see [execution plan §03](EXECUTION_PLAN.md#L33-L37). This document specifies target behavior and intended npm-facing paths, not a syntax migration, build result or promise about the current published package. No product, metadata or package changes are made here.

## Evidence and constraints

- Static CSS starts with light `:root` values and supplies `[data-theme="dark"], .dark` overrides for both palette scales and semantic values ([theme](../src/styles/_theme.sass#L7-L18), [dark theme](../src/styles/_theme.sass#L480-L490), [palette](../src/styles/_colors.sass#L693-L707)). README recommends `.dark` on body or `data-theme="dark"` on html ([README](../README.md#L270-L286)); demo toggles `.dark` on html and reads system preference once at mount ([demo](../examples/App.vue#L3342-L3348), [mount](../examples/App.vue#L3862-L3868)). These are source/docs facts, **not** tested equivalence of both selectors under custom colors.
- `applyTheme(colors, curve)` generates scales, writes active semantic/raw scale/alpha values inline on `document.documentElement`, writes both light/dark raw scales for inverse tokens and sets global surfaces/overlay ([generator](../src/utils/color-generator.js#L125-L135), [writes](../src/utils/color-generator.js#L185-L259), [background](../src/utils/color-generator.js#L265-L305)). It detects only `.dark` on html/body, observes only their `class` changes, and its initial observer callback closes over the **first** call's colors ([generator](../src/utils/color-generator.js#L129-L135), [observer](../src/utils/color-generator.js#L307-L322)). Thus mode/data-attribute/second-palette switching after an `applyTheme()` call cannot be claimed correct. `generateScale` currently ignores the `curve` argument ([generator](../src/utils/color-generator.js#L18-L21)); don't promise vivid/muted behavior until verified.
- Root package declarations list ESM/UMD, `./style.css`, a legacy `./dist/littlebrand-ui.css` alias and a bundled MCP CLI, but **not** an explicit root `types` export or component deep subpaths ([package](../package.json#L6-L27)). Vite's entry is `src/index.js`, which imports styles and exports named components, utilities and plugin ([Vite](../vite.config.js#L28-L42), [root](../src/index.js#L3-L4), [names](../src/index.js#L44-L54), [plugin](../src/index.js#L56-L102)). README recommends named root imports and the CSS path ([README](../README.md#L29-L82)). Source presence under `files` is **not** proof of consumer-accessible deep imports or working types; see [Step 01 distribution finding](audits/01-public-surface.md#L93-L96).

## Approved target theme behavior (requires implementation and tests)

| Situation | Target behavior | Compatibility/validation |
|---|---|---|
| No explicit theme selector, with or without `applyTheme()` | **Automatically follow the system preference** (`prefers-color-scheme`) at first paint and when it changes; light if the browser cannot report a preference. CSS-only consumers must not wait for JS to choose initial mode. | **Owner-directed change** from the checkout's light `:root` default. Verify initial paint, runtime custom palette, OS changes and SSR/hydration; document possible behavior change for consumers who relied on light by default. |
| `.dark` on `html` or `body`, or `[data-theme="dark"]` on `html`/`body` | Explicit **dark** for descendants, regardless of OS; both spellings remain supported. | Align CSS and JS under custom `applyTheme()`; test html and body separately. Do not remove `.dark`. |
| `[data-theme="light"]` on a subtree, including the root | Explicit **light** regardless of OS; a subtree `[data-theme="dark"]` wins over an ancestor's light. Nearest explicit mode wins; on the *same* node, `data-theme` beats `.dark` when they conflict. Removing an explicit choice returns that scope to its inherited/system mode. | Adding explicit light is an **approved target selector behavior**, not a current guarantee. Check specificity, inherited custom properties and transitions in a browser before documenting as shipped. |
| System preference and user choice | The library's **automatic** fallback tracks OS changes only where no explicit selector applies; host applications can set/persist an explicit light or dark selector for a user choice. No kit-owned preference persistence is proposed. Native-control `color-scheme` should match effective mode. | Current demo reads preference once at mount, and static CSS defaults light; neither meets this target ([demo](../examples/App.vue#L3862-L3868), [theme](../src/styles/_theme.sass#L10-L18)). Avoid JS-only first-paint flash or OS events overriding explicit choices. |
| `applyTheme({ primary: '#8b5cf6', ... })` | Keep this public API and the eight-family Step 02 mapping. Retain the **latest** supplied palette/background for subsequent mode changes; recompute/select values for the effective mode without reverting to the first palette or resetting other valid overrides. A second call replaces the prior custom palette as a whole (unspecified families use documented defaults). | Current observer captures first `colors` and watches only `class` ([generator](../src/utils/color-generator.js#L136-L149), [observer](../src/utils/color-generator.js#L307-L322)); this is target behavior, not current behavior. No new setter/reset API promised. |
| Nested preview and Dialog | A light preview inside a dark page (and vice versa) uses the **same custom brand** with mode-correct semantic and alpha values; root inline values must not pin nested preview to the wrong mode. A Dialog opened from that preview must receive its **originating scope's effective theme** (mode and custom palette) even when teleported to body; a document-level Dialog uses the document theme. Keep the Dialog and backdrop theme in sync if that scope changes while it is open. | **Owner-directed requirement, not current behavior.** `LbDialog` teleports to body ([Dialog](../src/components/Dialog/LbDialog.vue#L1-L8)); that portal leaves the preview's CSS inheritance. Provide a deliberate theme context to the teleported subtree; do not assume the nested selector alone suffices. Test backdrop compositing over the actual page, focus, alpha and on-fill in both modes. Popover content also teleports ([Popover](../src/components/Popover/LbPopoverContent.vue#L1-L9)), but broader overlay scope is a separate follow-up, not a verified guarantee here. |

**Ownership rule:** static CSS must define complete light **and** dark defaults and the approved Step 02 semantic names (including inverse dependencies) without JS, select the system mode when no explicit selector applies, and let explicit selectors override it. `color-scheme` should track the effective mode for native controls; the implementation must prevent a system-dark default from defeating an explicit light subtree. `applyTheme()` customizes that contract for the document and should produce **mode-aware values at the appropriate scope**, not a competing set of light-only root inline overrides. Switching mode changes which mode's palette is active; it must not wipe a host's unrelated CSS customizations. Component styles consume semantic `--lb-*` names rather than query JS mode directly. Dialog's teleported subtree must use the opener's effective theme scope without copying a stale one-time snapshot of individual CSS values; a system preference or custom palette change while open should remain reflected. Implementation may retain selector overrides or investigate `light-dark()` **only if** the same explicit light/dark, custom palette and nested-preview behavior survives; do not switch syntax merely to mirror Product Design Sandbox. Precise storage/style application and safe observation strategy belong to Steps 04, 06 and 07.

**Precedence cases to test:** no selector under system light, dark, then an OS change → root `.dark` → root `[data-theme="light"]` → root `[data-theme="dark"]`; both selectors on the same element; `.dark` on body under explicitly light html; nested dark inside light and nested light inside dark; replacing a palette after an observer exists; removing the explicit selector; and custom `background`/neutral over alpha surfaces. CSS inheritance and selector specificity make contradictory ancestor/root combinations particularly important. Do not promise the precedence table based on static inspection alone.

### Required written walkthroughs (target results, not runnable verified examples)

1. **System default → explicit light → explicit dark → system:** with no selector and CSS loaded, Button and Input follow system light or dark on first paint and after an OS change. On a dark OS, set `document.documentElement.dataset.theme = 'light'`: they switch to light despite the OS; set it to `'dark'`: they use dark scale and text/on-fill mappings; remove the attribute: they again follow the **current** OS mode without stale inline overrides. The `.dark` class on html or body must force dark regardless of OS when no conflicting `data-theme` is present.
2. **Custom brand, light → dark → light:** start explicit light; call `applyTheme({ primary: '#8b5cf6', neutral: '#64748b' })`. Button's fill and on-fill and Input's border/surface use custom **light** values. Change `data-theme` to `dark`: the **same brand inputs** yield dark values, alpha and inverse references remain valid. Change back to `light`: original custom light values return; no second `applyTheme()` call is required. Call `applyTheme({ primary: '#0ea5e9' })`, then toggle again: the **newest** palette wins rather than an observer restoring purple; omitted families follow the API's default inputs, not the previous call.
3. **Nested preview and Dialog:** custom-brand dark document contains `<section data-theme="light">` with Button, Input and an open-Dialog control; those components use custom-brand light values and the inverse token refers to its opposite mode. The Dialog panel **and teleported backdrop** receive that light preview's effective theme/palette despite mounting under body; a Dialog opened outside the preview uses dark document values. Reverse the modes (light document, nested dark preview) and change the preview mode or custom brand **while the Dialog is open**: its colors and focus ring stay in sync. Test backdrop alpha over the real page, keyboard focus and inverse/on-fill contrast. This is a required target, **not current verified behavior**; broader Popover/overlay propagation is separate.
4. **System-following versus saved choice:** an app with no saved user preference leaves the explicit theme selector unset; the UI kit CSS and runtime palette follow the OS, including subsequent changes. If the app stores a choice, it sets an explicit `data-theme="light"` or `"dark"`; OS events do not change that choice. Clearing it returns to system-following. The host owns preference persistence, not detection; this is a target behavior, not a currently verified kit feature.

## Recorded approval and deferred decisions

**Approved for planning:** no explicit choice follows OS preference **on first paint and on subsequent changes**; explicit `[data-theme="light"]`, `[data-theme="dark"]` and legacy `.dark` override OS (nearest explicit scope wins; `data-theme` wins on the same node). `applyTheme()` retains the latest custom palette across effective mode changes and a new call replaces the preceding palette. A Dialog opened from a nested scope receives its originating mode **and custom palette** through its body portal, including updates while open; a document-level Dialog uses document mode. Keep npm root named imports and `/style.css` canonical, and retain existing CSS alias/require path without adding exports. These are **targets**: current source does not meet all of them.

**Deferred, not silently guaranteed:** precise CSS/JS ownership and portal implementation, SSR first-paint/hydration strategy, theme behavior of Popover/other teleported overlays, and whether additional npm deep paths or type declarations can be supported. Verify in Steps 04–07 before promising TypeScript completion, nested overlay coverage, or package behavior. If consumer or browser tests show that the approved precedence or paths need a breaking change, bring a migration decision back to the owner rather than silently changing the contract.

**Next gate:** Step 04 adds non-writing parity/theme tests, Step 05 validates npm and type import behavior in a clean consumer (build only with explicit authorization), and Steps 06–07 align and verify the approved theme behavior. None of the written walkthroughs is a passing runtime test.
