# Step 06 — static and runtime semantic-token alignment

**Status:** implemented locally on `feat/step-06-token-alignment`, based on the [owner-approved Step 02 contract](STEP_02_TOKEN_CONTRACT.md). Nothing is published or merged. No production build, extraction or generated token/MCP metadata refresh was run for this step; those operations need separate owner authorization. Review after the prerequisite Steps 01–05 PRs.

## What changed

- The eight existing `--lb-*` color families retain their names. Family surfaces use **base/subtle/normal/hover/active = 1/2/3/4/5** in both static SASS and `generateSemanticTokens()`/`applyTheme()`. Previously runtime had no family `base`, and used `subtle/normal/hover/active = 1/2/3/4`; this is a **visual change after applying a custom palette**, not a token-name migration. See `CHANGELOG.md` for before/after steps.
- Runtime `--lb-surface-{family}-{normal,hover,active}-alpha` now references the active alpha primitives at steps 3/4/5. Runtime inverse base/subtle now references the opposite palette's raw 1/2 steps, following the static selectors. Direct `generateSemanticTokens()` callers can pass `'dark'` as the new optional fourth argument when producing dark-mode inverse references (the existing third argument remains accepted). `_colors.sass` now defines the needed raw **light/dark step 1/2 values at `:root`** even with JavaScript disabled. `applyTheme()` still sets light/dark raw scales for custom palettes. Existing runtime-only `border-subtle`, `surface-raised` and family `surface-disabled` remain untouched/unpromoted.
- `background` is a global canvas selector rather than a ninth family; a family name or custom hex source changes global `surface-base/subtle/disabled` (1/2/3) without inventing `--lb-background-*` primitives. Border focus stays step 7, fill states stay 9/10/8, neutral disabled alpha stays step 2, other disabled alpha step 4, and the three static shadows stay unchanged.
- `tests/token-alignment.test.js` compiles authored SASS **in memory** and machine-compares documented surface/fill/text/border roles, alpha/inverse references and raw dependencies for all eight families × both modes against generated tokens. It also checks custom-palette inline token values and background sources. Existing default on-fill anchor choices agree between static/runtime; the tests **do not measure contrast** or alpha compositing in a real browser. The old surface/alpha pinned gaps in `tests/theme.test.js` were replaced with positive assertions; selector and stale-observer gaps remain pinned for Step 07.

## Acceptance and follow-ups

`npm run lint`, `npm run typecheck`, `npm test` (21 tests), and `git diff --check` are the non-build checks. A separate owner-authorized build is needed to regenerate `TOKENS.md`, MCP token data and distribution CSS before any new tarball can be certified. [Step 07](STEP_07_THEME_RELIABILITY.md) now checks system preference, `[data-theme]`/`.dark` precedence, repeated `applyTheme()` and latest palette, real-browser inverse surfaces, per-state on-fill contrast, sampled alpha compositing over actual backgrounds, and focus visibility. Do not promote unverified runtime-only token names or promise WCAG contrast based on this source parity check.
