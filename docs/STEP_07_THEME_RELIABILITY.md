# Step 07 — theme reliability and browser verification

**Status:** implemented locally on `feat/step-07-theme-reliability`, dependent on Steps 01–06. No build, extraction, merge or publication was run for this step. The version already published on npm remains unchanged. See the [approved theme contract](STEP_03_THEME_DISTRIBUTION_CONTRACT.md) and [token mapping](STEP_06_TOKEN_ALIGNMENT.md).

## Implemented contract

- CSS-only consumers use `prefers-color-scheme: dark` at initial paint and when OS preference changes, with light fallback. `.dark` and `data-theme="dark"` remain explicit overrides; `data-theme="light"` is now an explicit override even on a descendant of a dark scope. On one element, `data-theme="light"` wins over `.dark`; the nearest explicit ancestor wins for descendants. `color-scheme` follows the resolved selector for native controls. SASS now reuses the dark scale/semantic declarations for the explicit and system-dark cases; root-only typography and sizing are not reset in a nested preview.
- `applyTheme()` continues to set active document values inline, but its current palette/background is now tracked across html selector and OS changes instead of restoring the first call. An injected scoped CSS rule provides the **same custom palette in both modes** to nested light/dark and body scopes, avoiding light values pinned by root inline declarations. This adds an inline `<style data-lb-custom-theme>`; applications with restrictive `style-src` CSP should review/allow their runtime theming policy before upgrading. The generated rule uses validated color-family identifiers and valid hex input. A second `applyTheme()` replaces the prior input; no persistence API was added.
- Dialog now has a hidden origin anchor and mirrors computed `--lb-*` properties and effective mode onto its teleported overlay. It observes the origin's ancestor selectors/styles, system preference and internal palette updates while open, and cleans up subscriptions on close/unmount. A document-level Dialog follows the document/body. This guarantee is **for Dialog**, not for Popover or other teleports.
- On-fill roles select the higher-contrast **white/black** anchor separately for the normal/hover/active fill in static light/dark themes and generated palettes. The existing `--lb-text-light-normal` and `--lb-text-dark-normal` anchor names now resolve to white/black; overriding those public tokens can change contrast. Button keyboard focus uses a high-contrast neutral inner outline alongside the existing brand focus color (still step 7). These are visual changes; see `CHANGELOG.md` for migration notes. The demo now follows OS changes until its toggle sets an explicit selection; a stale SASS variable in the demo was also corrected.

## Verification and limits

- `npm run lint`, `npm run typecheck`, `npm test` (21 tests) and `npm run test:browser` passed without a production build. The browser command uses pinned Playwright/Chromium, compiles SASS in memory for a CSS-only initial-mode test, starts an in-process Vite dev server for actual SFC/Dialog/teleport and demo checks, and closes both on completion. Install the matching Chromium browser in a fresh CI environment before running it; no browser binary is committed.
- Chromium measured all **8 families × 2 modes × 3 fill states (48)** at ≥4.5:1 with the authored static colors; a custom `applyTheme()` palette was also checked across all 48 states. A primary custom palette's alpha surface was composited over base and subtle backgrounds in both modes; its primary text exceeded 4.5:1 on both. A keyboard-focused Button's contrasting outline exceeded 3:1 against sampled custom light and dark preview backgrounds. These sampled browser measurements are not a guarantee for every arbitrary palette, surface, component, or browser engine.
- Remaining scope for later reviews: SSR/CSP integration and style-injection lifecycle, performance of large palettes and many simultaneous Dialogs, alpha/text contrast for *all* consumer palettes and backdrops, other teleported overlays, reduced motion, and broader keyboard/focus/a11y coverage in Step 08. The npm artifact and generated token metadata need a **new owner-authorized build** before release verification; the Step 05 artifact predates Steps 06–07. The MCP dependency audit findings from Step 05 also remain open.
