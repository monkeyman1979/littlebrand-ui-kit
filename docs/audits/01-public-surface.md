# Step 01 — public-surface triage audit

## Executive summary

At checkout `8b92965` (starting on `develop`, now `docs/step-01-public-surface-audit`), the source root names and globally registers **33 distinct Vue components/pieces**: 23 standalone and 10 pieces of four compound families. The secondary barrel names **32/33** (omits `LbDropdown`). There are **33 `.vue` files, 26 `.vue.d.ts` files, and 26 MCP component records**; the latter two cover the same 26 exported names, not 26 verified APIs. **Zero** `.vue` files are internal-only under this source-export definition. Counts describe this checkout, not the contents or behavior of the published npm tarball. Entry points: [root exports/plugin](../../src/index.js#L44-L102), [secondary barrel](../../src/components/index.ts#L1-L26), [extractor input](../../scripts/extract-components.js#L172-L188), [MCP data](../../mcp-server/src/data/components.ts#L52-L54).

Top risks: (1) static and runtime surface tokens disagree while runtime inline overrides can persist across mode changes; (2) MCP examples/API omit real slots/events and can suggest invalid variants; (3) root/secondary exports, type exposure, and catalog claims do not describe one dependable consumer contract. **Next:** review Step 02's token grammar and backwards-compatibility policy before changing names; schedule theme/consumer verification in Steps 03–05.

## Owner decisions and next PR

1. **Step 02 (next PR):** approve roles and palette-step mappings for the eight current families, especially surface `base/subtle/normal/hover/active`, alpha/inverse, text-on-fill and shadow/elevation. Should runtime match static defaults or is an explicit migration intended? Capture old → unchanged/alias/deprecated/replaced names; do not rename yet.
2. Decide whether all current `--lb-*` semantic names (including `--lb-text-on-*`, surface `*-normal-alpha`, inverse) stay public, and the compatibility/deprecation window and acceptable breaking-release boundary. Contrast, focus ring dimensions versus focus color, and alpha-over-background criteria need measurable acceptance cases.
3. For **Step 03**, specify default/system/light/dark selectors, nested overlays/previews and `applyTheme()` behavior on light → dark → light. Which selectors are supported for custom runtime palettes?
4. For **Steps 03–05**, confirm the supported npm root, CSS, type and optional deep import paths; whether exported compound pieces require parent-context examples; schedule a clean consumer fixture and decide who owns missing declarations/MCP entries.
5. Move **Step 04** metadata/example parity checks ahead of advertising or regenerating MCP content. Prioritize Button, Input, Dialog and Popover (or choose SegmentButton as the first compound slice); do not treat generated examples as verified documentation yet.

No product changes or release-note entry are warranted for this triage report. Review the Step 02 contract before implementing token/theme/API fixes.
